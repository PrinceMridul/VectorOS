# Limitations

This document exists because a repository that only describes what it does
well is not trustworthy, and we would rather this be too long than too
flattering. Everything here is either directly measured (a coverage number,
a file that doesn't exist) or a plain statement of what has not been done.
Where we're not certain, we say so instead of rounding to the nearer claim.

If you read one section before deciding how much to trust anything else in
this repository, read the first one.

---

## 1. No learning-outcome validation exists

This is the most important limitation and it should be read before any other
claim in this repository is taken as more than a hypothesis.

There is no control group, no pre/post test, no delayed-retention
measurement, and — as of this writing — essentially one learner's worth of
usage data, generated by the people who built the system. Every claim in
`README.md` and `DESIGN_DECISIONS.md` about *why* the architecture is built
this way is grounded in published learning-science research (retrieval
practice, the doer effect, productive failure, metacognitive calibration).
None of those citations are evidence that *this specific implementation*
produces the learning gains that research predicts for the underlying
techniques. Implementing an idea correctly and implementing it *effectively*
are different claims, and only the first one is supported here.

**What would close this gap:** a study comparing learners using this system
against a matched group using an unstructured assistant, with a delayed
retention test. Not built. See `FUTURE_WORK.md`.

## 2. The real LLM provider integrations are effectively untested

Measured via `pytest --cov`:

```
app/llm/gemini.py       39 statements    0% covered
app/llm/openai.py       34 statements    0% covered
app/llm/anthropic.py    40 statements    0% covered
app/llm/base.py         86 statements   55% covered
```

Every automated test, and the overwhelming majority of manual testing during
development, has run against `MockProvider`. This means the specific claims
made about resilience under pressure — the scaffold ladder holding, the
guard catching a leak, the refusal-and-pivot pattern working gracefully —
have been exercised against deterministic, non-adversarial text, not against
a real model's actual behavior when a real conversation gets difficult. It's
entirely possible the guard's cosine-similarity leak check behaves
differently in practice against real embeddings than it does in the tests
that exist. We don't know, because it hasn't been run.

**What would close this gap:** integration tests against at least one real
provider, and — more importantly — the adversarial evaluation described in
item 3.

## 3. The core safety claim has never been adversarially tested

The claim that this architecture resists "scaffolding collapse" better than
a prompt-only tutor is the central engineering claim of the project. It has
never been tested against a sustained, genuinely adversarial conversation
with a frontier model — no session has been run where an LLM plays a
frustrated, manipulative learner trying to extract the answer through
persistence, roleplay, or prompt injection, with the number of turns to
failure recorded and compared against a prompt-only baseline.

Everything that *can* be said today about this claim is structural: there is
no code-level transition from "challenge issued" to "answer given," and that
fact is independently verifiable by reading `pedagogy/state_machine.py`. That
is real and it is not nothing. It is also not the same claim as "we tested
this against pressure and it held," and the two should not be conflated.

## 4. Knowledge-tracing parameters are not fit to data

`BKTParams` defaults (`prior=0.15, learn=0.30, guess=0.20, slip=0.10,
forget=0.05`) are literal constants chosen for plausibility, with a written
rationale for each, and are not fit via expectation-maximization or any other
method against real learner response sequences — because no such dataset
exists yet for this system. The extensions to classic BKT (confidence
weighting, scaffold discounting, the measurement/learning-transition split)
are architecturally sound fixes to known failure modes of the textbook
formulation, verified by unit tests against synthetic scenarios. Whether the
*resulting numbers* are accurate estimates of what a real learner knows has
not been checked against any ground truth, because no ground truth currently
exists to check against.

## 5. The cognitive-load estimate is an unvalidated heuristic

`pedagogy/load.py` computes a 1–9 number from task difficulty, recent
accuracy, interaction latency, and task type. The range and general shape
were inspired by Paas's subjective mental-effort rating scale. **This is not
the Paas instrument** — Paas is a self-report question asked of the learner
after a task; this is a formula over behavioral telemetry with coefficients
we chose. An earlier draft of the documentation (and the code comments)
called this "the Paas scale," which was an inaccurate claim and has been
corrected throughout the codebase (`load.py`, `models.py`,
`session/service.py`) and this documentation set. The heuristic itself has
not been validated against any ground-truth measure of cognitive load —
including the actual Paas instrument, which would be the natural thing to
validate it against and has not been run.

## 6. Misconception detection depends heavily on which provider is running

Offline (`MockProvider`, the path essentially all testing has used):
misconceptions are detected via `re.search` against author-written trigger
phrases in each concept's `misconception_bank`
(`llm/mock.py::_match_bank`). This is closer to a keyword-triggered rule
system than to open-ended classification. It is deliberately conservative —
biased toward missing a misconception rather than inventing one, because a
false positive writes a permanent-feeling gap into a learner's record — but
it will not generalize to phrasing not anticipated by the authored triggers.

On a real model: the Examiner reads the same misconception bank as reference
material and classifies more flexibly. This path is real and implemented,
but essentially untested (see item 2) and has never been compared against
the offline path for diagnostic accuracy or against a held-out set of real
learner responses for precision/recall.

## 7. The Metacognitive Gate's scoring is lexical, not semantic understanding

The free-recall check (`reflection_pass_threshold = 0.6`) scores a learner's
memory-based explanation by lexical concept-coverage against the reference
model, offline, or by an LLM judgment on a real provider (again, untested —
see item 2). The offline path can be fooled by a learner who uses the right
vocabulary without genuine understanding, and can under-credit a learner who
explains the idea correctly in different words than the reference model
uses. This is a known, structural limitation of lexical matching, not an
edge case.

## 8. Content is small and hand-authored

Three learning graphs, seventeen concepts total, each authored by hand
(`db/seed_data.py`, roughly 1,200 lines). Authoring one concept — its
canonical model, misconception bank with trigger phrases, probe questions,
and challenge seeds — took meaningful person-time per concept. There is no
tooling to accelerate this, and no evidence yet about whether an
LLM-assisted authoring pipeline would produce content of comparable quality.
This is the most direct constraint on how far the current system could scale
as a product without further work.

## 9. No security or auth model suitable for real users

Identity is a long-lived (180-day) signed bearer token stored in browser
`localStorage`, with no refresh mechanism, no revocation path, and no
password. This is a reasonable choice for a self-hosted demo and not a
reasonable choice for a system that would hold a real person's longitudinal
learning record — which is exactly what this system's core value proposition
requires it to hold. There is no rate limiting, no per-user or per-session
LLM cost ceiling, and no data-retention or deletion policy implemented.

## 10. No production operational tooling

- **No database migrations.** Schema changes happen via `create_all()` at
  startup, which works for a single-developer SQLite setup and is not a
  credible path for evolving a schema against a populated Postgres database.
- **No CI.** Nothing in the repository automatically runs lint, type
  checking, or tests on a change. Every quality gate referenced in this
  documentation (`make check`) has been run manually.
- **No cost telemetry.** `agent_events` records `tokens_in` / `tokens_out`
  per call, but nothing aggregates this into a per-session or per-learner
  cost figure. We do not know, in dollar terms, what a 25-minute session on
  a real provider costs, because it has never been measured end to end.

## 11. Frontend has no automated test coverage

Zero test files under `frontend/src` as of this writing, across
approximately 4,300 lines of TypeScript/TSX. Correctness of the client has
been verified by manual interaction and by type-checking (`tsc --noEmit`),
not by any automated regression suite.

## 12. Built subsystems with no consumer

`pedagogy/schedule.py` computes spaced-repetition due dates
(`review_due_at`) and can build an interleaved review queue
(`build_review_queue`). The dashboard surfaces this data. Nothing in the
product currently delivers a review to a learner outside of them navigating
to the dashboard themselves and choosing to open a due concept — there is no
notification, email, or push mechanism. The scheduling math is implemented
and tested; the delivery loop it exists to support is not.

## 13. No instructor- or cohort-facing surface

Every screen in this product is learner-facing. There is no way for a
teacher, parent, or curriculum author to see aggregate misconception
coverage across a group, review what the system diagnosed for a specific
learner, or intervene. For a product whose own research grounding names
teacher-in-the-loop collaboration as a core value, this is a real gap
between stated philosophy and shipped surface area.

## 14. Content updates don't propagate to existing learners

`clone_template` deep-copies a template graph — nodes, edges, and content
chunks — into a learner-owned graph the first time they start a goal. If a
concept's canonical model or misconception bank is corrected after a learner
has already started that goal, their copy does not update. This is a real
architectural gap, not a deliberate design choice.

## 15. Everything above should be read together

None of these limitations individually is disqualifying for a project at
this stage. Read together, they describe a system whose *engineering
discipline* is ahead of its *evidence base* — the code is more rigorous than
what has been shown about whether it works. We think that is the honest
description of where this project currently stands, and we'd rather state it
plainly than let the quality of the architecture imply a validation status it
does not have.

See [`FUTURE_WORK.md`](FUTURE_WORK.md) for which of these we intend to
address, in what order, and which remain open research questions rather than
engineering tasks.
